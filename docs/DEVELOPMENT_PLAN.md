## 1. 목표와 범위

### 1.1 프로그램 목표
시뮬레이션 매니저는 HILS 링 구조에서 **환경 제공자·기록자·심판** 역할을 수행한다:

1. **가상시계·가속엔진** — 가상 1개월을 실 수 시간으로 압축(예: 실 10 s = 가상 15분), Run 중 자유진행
2. **환경 배포** — 시나리오 DB(기상·부하)에서 가상 1분마다 링크①·③ 레지스터 갱신
3. **연결중개** — RTDS 기동 감지 → EMS에 'RTDS 준비됨' 통지 → EMS–RTDS 직결 유도
4. **생존감시** — EMS·RTDS Heartbeat 관측, 단절 판정·이벤트 기록
5. **Historian** — 계측·예측·상태 시계열 적재, 예측-실적 페어링
6. **Run 관리·평가** — Run A/B 오케스트레이션, 피크·요금·예측률 비교 리포트
7. **웹 대시보드** — 다른 PC 브라우저에서 접속하여 모니터링·제어

**비범위(Non-goals)**: EMS의 예측·최적화 로직과 RTDS의 전력계통 모델은 각각 별도 PC의 외부 시스템이다. 본 프로젝트의 에뮬레이터는 **시뮬매니저 검증용 간이 구현**일 뿐 실제 EMS·RTDS를 대체하지 않는다.

### 1.2 운영 환경
- 3노드 별도 PC: 시뮬매니저(192.168.0.10) · EMS(192.168.0.20) · RTDS(192.168.0.30), Modbus TCP 502/Unit 1 (협의 가능)
- 시뮬매니저 PC: Windows, Python 3.11+, 브라우저 접속용 웹 서버(0.0.0.0 바인딩)
- 개발 단계: 단독 PC에서 매니저 + 에뮬레이터 2종으로 전체 시퀀스 재현

## 2. 시스템 아키텍처

### 2.1 Backend 모듈 구성

```
                    ┌──────────────────────────────────────────────┐
                    │              FastAPI (app/main.py)           │
                    │   REST API (제어·조회)   WebSocket (실시간)   │
                    └───────────────┬──────────────────────────────┘
                                    │ 이벤트 버스 (asyncio)
   ┌────────────┬───────────────────┼───────────────┬──────────────┐
   │ clock/     │ sequence/         │ watch/        │ historian/   │
   │ 가상시계    │ P0~P6 상태머신    │ HB 생존감시    │ SQLite 적재   │
   │ 가속엔진    │ 연결중개·핸드셰이크│ 단절 판정      │ 페어링(B-9)  │
   └─────┬──────┴────────┬──────────┴───────┬───────┴──────┬───────┘
         │               │                  │              │
   ┌─────▼───────────────▼──────────────────▼──────┐  ┌────▼────────┐
   │ modbus/  링크① 서버(EMS용) · 링크③ 서버(RTDS용)│  │ evaluation/ │
   │ 뱅크 라우팅 · read/write 후킹 · 변경 이벤트      │  │ §7 지표 산정 │
   └─────────────────▲────────────────────────────┬─┘  └─────────────┘
                     │ 레지스터 정의 참조           │
   ┌─────────────────┴─────────┐   ┌──────────────▼──────────────┐
   │ protocol/  레지스터 맵 SSOT│   │ scenario/  시나리오 DB       │
   │ 주소·타입·스케일·부호 상수  │   │ CSV 임포트·보간·1분 배포      │
   └───────────────────────────┘   └─────────────────────────────┘
```

- **이벤트 버스**: 가상시계 틱(1분/15분/일 경계), 레지스터 쓰기 감지(RTDS 운전중, HB, ack 등), 단절/복구 — 모듈 간 결합을 이벤트로 분리. WebSocket 스트림도 동일 버스 구독.
- **protocol/ = 단일 소스(SSOT)**: 엑셀 프로토콜맵의 모든 레지스터를 Python 상수(dataclass)로 정의 — 링크·객체유형·주소·명칭·타입·스케일·단위·범위. 매니저 서버, 에뮬레이터, 테스트가 전부 이것을 import. 스케일 인코딩/디코딩 함수(`encode(value, reg)`, `decode(raw, reg)`)도 여기에 둔다.

### 2.2 프로토콜 구현 설계 요점

| 항목 | 설계 |
|---|---|
| 링크①·③ 뱅크 분리 | 매니저는 링크당 독립 데이터스토어(뱅크) 보유. 기본: 단일 포트 502에서 **클라이언트 IP로 뱅크 라우팅**(EMS IP→뱅크①, RTDS IP→뱅크③). 설정으로 **링크별 포트 분리**(시험 기본: ①=7000, ③=5021) 선택 — 에뮬레이터가 같은 PC(127.0.0.1)일 때 필수 |
| 링크① DI/IR 쓰기(EMS→매니저) | Modbus 규격상 Client는 DI/IR 쓰기 불가 → **HR 미러 방식**: EMS가 합의된 미러 HR 주소(예: DI 100000→HR 410000, IR 300000→HR 430000, 오프셋 협의)에 FC16 기록, 매니저가 내부적으로 DI/IR 뱅크에 매핑. 미러 오프셋은 `protocol/mirror.py` 상수(매니저·에뮬레이터 공용 import) — 합의 변경 시 이 상수만 갱신 |
| 링크③ RTDS→매니저 쓰기 | HR(FC16)·Coil(FC05) — 규격 정합, 그대로 구현 |
| read/write 후킹 | pymodbus 데이터스토어를 상속해 쓰기 발생 시 이벤트 발행(예: ③Coil 000000=1 → 연결중개 트리거, ③HR 400000 변화 → HB 갱신) |
| 폴링·타이밍 | 매니저는 Server라 폴링 없음(클라이언트가 옴). 가상 1분 틱마다 뱅크 갱신. 구간 경계 원자성: 시각·기상 갱신 **후** 구간 인덱스 갱신 |
| 타이밍 파라미터 | 응답 타임아웃 1,000 ms·재시도 3회·재접속 1~5 s·HB 1 s/판정 3 s — config 기본값 |

### 2.3 설정 파일 (config/default.yaml 초안)

```yaml
network:
  bind: 0.0.0.0
  mode: single_port      # single_port(IP 라우팅) | per_link_port
  port: 502              # single_port 모드
  link1_port: 7000       # per_link_port 모드 (EMS측, 시험 기본 7000)
  link3_port: 5021       # per_link_port 모드 (RTDS측)
  ems_ip: 192.168.0.20   # single_port 모드의 뱅크 라우팅 기준
  rtds_ip: 192.168.0.30
  unit_id: 1
simulation:
  start_virtual_time: "2025-07-01T00:00"
  days: 30
  accel_seconds_per_15min: 10   # 실 10 s = 가상 15분
  initial_soc: 50.0
  soc_max: 90.0
  soc_min: 10.0
  charge_limit_kw: 250.0
  discharge_limit_kw: 250.0
timing:
  response_timeout_ms: 1000
  retry_count: 3
  reconnect_interval_s: [1, 5]
  heartbeat_period_s: 1
  alive_timeout_s: 3
  disconnect_budget_intervals: 14   # Run 무효 판정(총 구간의 0.5%)

  interpolation: hold    # hold(ZOH) | linear — 두 Run 동일 적용
```

## 3. 단계별 개발 계획

각 Phase는 독립적으로 완료·검증 가능하도록 구성한다. 완료 기준(DoD)을 만족하면 CLAUDE.md 체크박스를 갱신한다.

### Phase 1 — 기반 골격 (프로젝트 스캐폴드 + 가상시계)

**목표**: 개발 뼈대를 세우고, 시스템의 심장인 가상시계를 먼저 완성한다.

| 구현 항목 | 내용 |
|---|---|
| 모노레포 스캐폴드 | `backend/`(FastAPI + pyproject.toml), `frontend/`(Vite React TS), `emulators/`, `data/`, `docs/` |
| protocol/ 레지스터 맵 | 엑셀 프로토콜맵 전체를 dataclass 상수로 코드화 (링크①: Coil 6·HR 12·DI 4·IR 19 / 링크②: Coil 6·HR 12·DI 6·IR 37 / 링크③: IR 12·DI 3·HR 6·Coil 2), 스케일 encode/decode + 32-bit big-endian 결합 함수, 단위 테스트 |
| 설정 시스템 | YAML 로드(pydantic-settings), §2.3 스키마 |
| 가상시계 엔진 | 시작/정지/일시정지/되감기, 가속배율 환산(가상 1분 = 실 배율/15 초), 1분/15분(구간)/일 경계 틱 이벤트, 구간 인덱스 0~95 |
| REST API 최소 | `GET /api/status`(가상시각·구간·상태), `POST /api/clock/{start|stop|pause|resume}` |
| 최소 UI | 가상시각·구간 인덱스·가속배율 표시 + 시계 제어 버튼 (WebSocket 1종) |

**DoD**: 브라우저에서 가상시계 기동 → 가상시각이 가속되어 흐르고 구간 인덱스가 96 랩어라운드하는 것 확인. 레지스터 맵·스케일 변환 단위 테스트 통과 (특히 INT16 음수, ×10/×100/×1000/×50 왕복, UINT32 상위워드 우선).

### Phase 2 — Modbus 서버 계층

**목표**: 매니저를 실제 Modbus TCP Server로 만든다.

| 구현 항목 | 내용 |
|---|---|
| 링크①·③ 서버 | pymodbus 비동기 서버, 뱅크(데이터스토어) 2식, single_port(IP 라우팅)/per_link_port 모드 |
| read/write 후킹 | 커스텀 데이터스토어 — 클라이언트 쓰기 시 이벤트 발행, 매니저 내부 쓰기 API(`bank.set(reg, value)`) |
| DI/IR HR 미러 | 링크① EMS 쓰기용 미러 HR 영역 → DI/IR 뱅크 내부 매핑 (오프셋 config) |
| Heartbeat 감시 | ①IR 300000(EMS)·③HR 400000(RTDS) 갱신 관측 → 3 s 판정 → 연결상태표·단절/복구 이벤트 |
| 연결상태 API/UI | 노드별 접속·HB·생존 상태를 REST/WebSocket + 대시보드 표시 |

**DoD**: 범용 Modbus 클라이언트(예: modpoll, QModMaster) 또는 pymodbus 스크립트로 두 링크에 접속해 읽기/쓰기 성공. HB 중단 시 3 s 내 단절 판정이 UI에 뜨는 것 확인.
